# Release notes draft

Generated by Codex from code changes; not yet reviewed.

v0.1.0 → `f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96` · SDK `0.2.0`

## Pico

- Add `--single-arm` to control a standalone arm through an SDK `Single` instance using the physical right controller. Left-controller readiness is unnecessary. Mapping uses `base` without the B3 mount transform; `--operator-frame face-to-face` keeps the same selected hand. Dual-arm ServoP remains the default. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- Add `--single-mapping-yaw` to rotate translation and rotation increments around base Z in single-arm mode. Its range is `\[-180,180\]` degrees, defaulting to `0`; `-90` is clockwise viewed from +Z. It does not modify cabinet frames or URDF. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- Add `--no-gripper` to skip DH gripper initialization and Trigger control in single- and dual-arm modes. With the gripper enabled, single-arm mode uses right Trigger edges to toggle it. In ServoP, thumbstick Y controls J6 while right Grip is held. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- Add single-arm `--control-mode fdcc`. It enters mode 6 through `EnableFdCartesianAdmittance` and calls `SetFdCartesianAdmittancePoseTarget` with Manual input and zero target wrench, at up to 50 Hz. Thumbstick J6 is disabled in this mode. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- Add single-arm `--control-mode impedance`. It enters mode 5 through `EnableCartesianImpedance` and updates equilibrium poses through `SetCartesianImpedanceTarget` over DDS, at up to 200 Hz. `--impedance-stiffness` and `--impedance-damping` accept six XYZ/RX/RY/RZ values, defaulting to `120,120,120,20,20,20` and `20,20,20,1,1,1`. Thumbstick J6 and FDCC virtual target extrapolation are disabled. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- FDCC and impedance targets start at measured TCP and have target speed and acceleration limits. FDCC defaults to `0.30 m/s`, `1.2 m/s²`, a following gain of `8/s`, and target velocity feedforward of `0.5`. `--fdcc-target-scale` optionally adds up to 30 mm of translation lead; it is disabled by default. Impedance defaults to `0.15 m/s`, `0.6 m/s²`, and `8/s`. These settings shape targets and do not guarantee measured motion. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- Releasing Grip in FDCC or impedance requests mode exit and waits for mode 0 before holding, while retaining the connection and motor enable. Re-gripping reanchors from measured TCP. Input loss, tracking loss, stale Jacobian data, or rejected candidates require fresh released-Grip input before resuming; late approvals cannot restart motion. Application exit requests motor disable. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- FDCC and impedance track input receive deadlines separately from target approvals. With fresh input but no new approval for 200 ms, they freeze the last sent equilibrium while retaining the mode, then resume after a successful check. Both use measured-Jacobian slowdown without the candidate endpoint condition-number-60 veto. Finite-value, IK reachability, joint-clearance, and FK-consistency checks remain. ServoP retains its original candidate-check policy. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- Strengthen numeric checks in Pico teleoperation. Nonfinite input and invalid quaternions are rejected before mapping and gripper-edge processing, and ServoP/ServoJ target values are checked before sending. Single-arm mode ignores the unused left controller. Modes, shaping parameters, impedance K/D, and mapping yaw are validated before connection; `--help-advanced` lists tuning options. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))
- Add compliance diagnostics separating raw target error, virtual lead, shaping gap, and following error. Logs also report target linear/angular speed, check waits, IK/FK durations, and pause reasons. `rpc_ms`/`send_ms` measure SDK call duration; DDS writes have no delivery acknowledgement, and these fields do not measure physical motion latency. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))

## Python interfaces

Control logic resides in the C++ bridge; this range adds no Python reader or native Python compliance implementation. ## SDK, build and release

- Fix shared-library consumers being required to discover private dependencies when using `find_package(smrcore_peripherals CONFIG)`. Shared package configuration no longer calls `find_dependency(Threads)` or `find_dependency(nlohmann_json)`. Static packages still resolve both dependencies, and the exported target remains `smrcore::peripherals`. ([abe9328](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/abe93282b2a87a92ddf010986665f6be9263c656))
- CI now collects the entire `unittests` directory and installs Eigen headers for the added offline Pico mapping, numeric-input, and compliance lifecycle regression cases. The release workflow still builds SDK bridge packages with `--with-pico OFF`. The new Pico control entry points require a compatible SDK and a source build with `--with-sdk ON --with-pico ON`; update the executable and `libsmrcore_pico_teleop.so` together. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))

## Documentation

They also describe SDK/cabinet requirements, diagnostic fields, and source-build delivery. ([f6e46d1](https://github.com/zhanhui-li-smore/smrcore_peripherals/commit/f6e46d1afa1ea5240ad1a5d45b391ac2a308bb96))

## Needs verification

- This draft is based only on code and documentation review within the specified range. No builds, tests, or hardware checks were run. Added offline cases and CI configuration do not establish hardware tracking, contact behavior, CST transitions, or physical safety.
- Documentation references SDK 0.2.0 for building, but this range does not establish that users' released SDK binaries and target cabinets provide the invoked FDCC/impedance APIs. CST support, dynamics models, and payload configuration for impedance still require confirmation in the target environment.
